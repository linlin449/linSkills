# 生成式软件工程 03 · 软件仓库管理

> 一句话：表面在讲 Git，实际在讲"怎么把一个软件项目组织成**一堆可以审计、可以回退、可以并行推进的小步快照**"。Git 是这句话的最优解，其余所有命令都是这句话的推论。

## 开场：GPT-6 发布了，但品位还没学会

第三讲开课时 GPT-6 刚发布，蒋炎岩的评价是"有惊喜，但编程提升有限，还没学会品位"：

- **代码越来越难读**：从 GPT-5 到 5.6 再到 6，思维链越来越紧凑、代码越来越紧凑，人根本没法 review。他干脆放弃 review，"只要写对就行"。
- **最大的惊喜是空间感知 + 数学能力**：能判断鲁班锁怎么抽第一块、骰子展开图对不对。OpenAI 的路线是"先学数学"（数学有全球共识的 verifier），学会后其他能力靠强化学习泛化出来。
- **直接冲击具身智能**：GPT-6 是语言模型，一帧一帧判断下一步，就能控制机械臂抓取、叠衣服。他半年的 3D 打印项目（光栅纸玩具），被 GPT-6 one-shot 直接搞定，直言"开始心疼自己的 PhD student"。

## 汽车类比：AI 时代还要不要学？

这是全讲最漂亮的比方：

- 一百年前汽车开 12 公里就坏，**每个司机都得懂汽车原理**才能修。所以那时候"想开车就得学原理"。
- 今天在地下车库说一句"帮我开到某地"，自动驾驶就出发了——**你完全不懂系统栈也能开车**。
- AI 就像更强大的汽车：替代的不只是腿，还有智力。**那还要不要学？他的答案：现在要学，因为学过才能更好地解锁 AI 的创造力；但以后怎么学，他也不知道。**

## 什么是"一个软件工程项目"

- 从空目录开始。你看到老师/同学给的 GitHub 链接，网页对人友好，你就知道"我的目录里也该有这些文件"。
- **项目 = 一个目录 + 一堆文件**，最终变成一个可交付的东西。经典笑话："GPT-6 太厉害了，我又做了好多 killer 产品，都放在 `http://localhost:5173`。"——发 Twitter 前要知道，**localhost 只有本机打得开**，别人看不到，这是必须内化的知识。
- **什么是软件**：标准定义是"代码、文档等一切与软件相关事物的集合"，但他的定义更好记——**软件是人类世界的需求在信息世界里的投影**。今天看到的投影，就是一个目录。

## Git 之前的黑暗时代

- 他第一个 PhD 学生 2012 年大一时，把代码存 U 盘，大二 U 盘坏了，启蒙作业全没了。
- 交作业的方式：打压缩包发邮件、网页上传；老项目"作业 V1、V2、作业最终版"，每次复制一个目录。
- **今天有了标准答案：Git。** 它能保存目录，还能**保留、比较、恢复历史版本**。用 `git clone` 发作业、`git pull` 更新作业，比给每个人发压缩包高效得多。

## 惊人的注意力：从 GitHub 上学品位

这是全课反复强调的"学习意识"，第三讲给了最具体的版本：

- **别把自己强化学习成"只听老师话的 AI"**：老师说"把作业拉下来"，你就只拉作业、绝不多看一眼——这跟被 RL 训练的 AI 一样，最省时间。多花一秒点进去看，可能发现"这个 README 写得好"。
- **从对比中学习**：香港路牌——走到岔路口，正前方一定有块牌告诉你三个路口各通向哪；南京地铁——要找出口得环顾四周找地图。**做 UI/README 也是同理：站在人的角度，用最少的方式把 A、B、C 全部呈现出来。** 今天 GitHub 上满是"巨长 + Unicode 框图"的 AI slop README，突然看到一个维护十几年的老项目、README 短但有三个清晰链接，你就学到了。
- **"上课耽误学习"是真的**：课外信息的密度远超课堂——打开一个成熟 GitHub 项目，你面对的是工程师十几年的心血（可能十年前崩溃过一次才有的重构）。传统教学没教你怎么利用这些。
- **学习方法：virtual implement（虚拟实现）**：看到一个方案前，先自己想"如果是我会怎么做"，再对比。一致=掌握了；教科书更好=追问它怎么想到的；**你的更好=一万次才有一次的正反馈，但会让你想去做更好玩的东西。**

## 你也能发明 Git：从需求推到第一性原理

- 需求：想回到上一个版本、和室友同步时两个人改同一个文件怎么办。**从"我要管理目录的版本"这个需求出发，一个大学生就能推导出简化版 Git。**
- **SVN 走错了路**：它存的是"变化"（delta，每改一行存一个 patch），看起来高效，但想回到早期版本就得逐个往回退，项目一大会把你拖进泥潭。
- **Git 的第一性原理**：我想回到过去某版本，就应该**一秒回去**。所以 Git 存的是**快照（snapshot）**，不是 delta。
- 历史：Linux 之前靠邮件列表发补丁（像"作业 V1/V2"），后来用 BitKeeper，Linus 受不了了，2005 年造出 Git——**它比我们想象的年轻得多**。

## Git 上手四件套 + 两个关键认知

- `git init` 后目录里出现一个默认隐藏的 `.git` 目录，项目就变成被版本管理的 repo。
- `git add`（暂存）、`git status`（看工作区）、`git commit`（创建带消息的快照）、`git push`/`git pull`。
- 认知 1：**不要把它当"作业 V1/V2/V3"用。** 正确用法是：每次改动（改文件、修 bug、加功能）都**及时小步 commit**，并在 message 里写清楚做了什么。
- 认知 2：**不懂就随时问 AI**（"我这个 commit 符合 best practice 吗？"），比闷头猜快得多。

## Commit Message 是项目的"历史轨迹"

- 一个 commit 从 V1 变 V2，message 描述"这次改了什么"。**沿着 message 一路读，就能看到项目怎么长成今天这样**：修过多少 bug、加过什么需求、经历过什么重构。
- 如果一万个提交都写 "I did some cool stuff"，commit message 这个特性就不该存在——直接 V1 变 V2 就够了。
- 规范是 **Conventional Commits**：以 type 开头（feat/fix 等）、可带 scope、冒号后一定要有空格，一行 headline + 详细 body。细节还有：中英文之间加空格（他用"高血压"形容不一致的空格）、body 里写 `Fixes #3` 能让 GitHub 自动 close issue。
- **空提交（empty commit）**：偶尔用来"finalize 一个版本"、触发 CI/workflow（把 bug fix 和 release 两个提交分开），但绝不能大量制造。

## git add . 的代价：什么不该进版本库

- `git add .` 合法且方便，但会把**编译产物**（`hello` binary、`dist`、`log`）也加进去——它们应该进 `.gitignore`，由构建系统生成。
- 为什么产物不该进库：一百个合作者环境不同，build 出的东西不同（带日期/hash/本机指纹），会产生**二进制冲突**，而二进制很难合并。
- 但没有绝对规则：`package-lock.json` 或生成的 header 有时反而该 check in（让别人不装工具链也能编译）。
- **高血压时刻**（新同学进组常见的坑）：提交了 `dist`/`log`、VS Code 个人设置（含 `C:` 硬编码路径）、**活着的 API key**（他看到 DeepSeek key 就知道"是位中国兄弟"）、Mac 的 `.DS_Store`（Finder 自动留下的隐藏索引文件）。

## 让 AI 当代码审查员：bisect 与 blame

- 现在可以让 AI 按 best practice 帮你做 Git，甚至重写历史。但**只有确认没有别人持有这段历史时才安全**（有 remote 时重写历史很糟）。
- AI 还知道一个反直觉的点：**每次提交都应该是"能构建、能测试"的完整自洽快照**——因为有人要用 `git bisect`。
- **`git bisect`**：把提交历史当成一个数组，某次提交引入了 bug，用二分查找定位"第一个坏提交"。想象"前缀全 0、后缀全 1"的数组找第一个 1。
- **`git blame`**：看每一行代码来自哪次提交、谁改的。二者配合，bug 就"冤有头债有主"。

## Git 的底层数据结构：blob / tree / commit

这是 Git 真正的工作原理，一句话讲清：

- Git 是**持久化数据结构**，持久化的是**目录树**。三类对象：**blob**（字节序列）、**tree**（目录节点）、**commit**（一次提交），全部按 hash 索引存在 `.git/objects` 里。
- 从 V1 到 V2，只改了 `B.txt`，那**只需要新建 `B.txt` 并复制"从它到根"的那条路径**，没变的 `A.txt`、目录 `D` 仍用指针指回旧版本。代价极小。
- 现场演示（他 vibe code 了一个 `gitv` 可视化工具）：解压一个 blob 能看到 `blob 15` 开头 + 正文；tree 里 `100644`/`100755` 是 mode；**分支是 refs 下的一个文件（指向 commit 的指针），HEAD 是指向指针的指针**。
- merge conflict 的现场：index 里悄悄存了 base/ours/theirs 三个版本，工作区文件里是尖括号冲突标记。**Git 的设计原则和香港路牌一样：在事情发生的地方，把处理所需的全部信息都放进来。**

## 架构自己把关，其余外包给 AI

他教三、四年级小学生 Python，vibe code 了一个极简 Web IDE（可视化汉诺塔、插入排序、3D 打印方块）。关键不在"它能跑"，而在**架构是他把关的**：

- **接口全部设计成 functional（pure function）**：trace 是纯函数，用标准的 derivation graph 展开。
- **所有会全局互相影响的状态，注册到一个全局位置**：playground 的核心共享状态只有十几行 + 十几行组装代码，其余全是黑盒子。
- **要求 Agent 只许看接口、禁止看库实现**：这样省 token，几万个 token 就做出整个 playground。

> 这是全课最实用的工程经验：**架构设计阶段用高智力模型和你讨论（设计不好后面就是无穷迭代）；把接口做成纯函数、状态集中管理；再开多个 agent 并行，`AGENTS.md` 里写明协作规则。**

## 为什么小步提交（Commit Often, Perfect Later, Publish Once）

- 复杂项目里改得越多、错得越多。一个一万行的 commit 引入一百个 bug，之后全怪它，修都修不过来。
- **每个 commit 只做一件事**：bug 是这次提交引入的，修完两个 commit 配对，能审计、能 bisect、能 blame、冲突也好解决。
- **立即 push = 免费备份**：电脑马上坏了也不丢工作。
- 小步提交还能**省 token**：AI 维护项目时不用重读无关文件。

## 总结：本讲真正要记住的

1. **软件 = 人类需求的投影**，一个项目 = 一个目录 + 一堆文件 + 可交付的东西。
2. **Git 的本质 = 把项目组织成"由 atomic change 推进的一系列快照"**。其余命令、分支、合并、冲突、bisect、blame，全是这句话的推论。
3. **存快照不存 delta**，这是 Git 对 SVN 的第一性原理胜利；底层就是 blob/tree/commit 三件套的持久化目录树。
4. **best practice 都是血泪教训**：及时小步 commit、Conventional Commits、generated file 进 `.gitignore`、别提交 API key/.DS_Store、每次提交都能构建测试。
5. **学习意识 > 具体知识**：用 virtual implement 和"对比学习"从别人的 repo 里偷品位；多花一秒点进去，别当"只听老师话的 AI"。
6. **架构自己把关，代码外包给 AI**：接口纯函数化、状态集中化，再用多个 agent 并行推进——这是 AI 时代真正的"项目管理"。
