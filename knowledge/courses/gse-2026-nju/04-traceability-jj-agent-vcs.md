# 生成式软件工程 04 · 软件仓库管理（2）：Traceability 与 jj

> 先记一句话：**保存代码还不够，还要知道它为什么存在、怎样检查，以及怎样和别人的修改接起来。**

第三篇讲“存档”。这一篇讲“联系和协作”。不需要先会 jj 命令，也能理解这些问题。

## 1. 功能改了，为什么文档和测试也可能要改

你做了一个学习助手，原来规定“记住所有偏好”。后来发现，有些偏好只在这周有效，于是改成“偏好可以过期”。

你改了代码，但说明书还写“永久保存”，测试也只检查永久偏好。三份内容开始说不同的话。

我们需要知道：

```text
这个需求 → 哪段代码负责？
这段代码 → 用哪个测试检查？
这份说明 → 解释的是哪个行为？
```

**Traceability，可追踪性**，就是维护这些联系，让你能顺着找，也能反过来找。

它像课本知识点与练习题的对应表：知识点变了，知道该重看哪些题，而不是把所有材料翻一遍。

## 2. 文件夹能分类，但联系不只是一种分类

目录适合回答“文件放在哪里”。但同一个测试可能检查多个功能，同一个功能可能涉及多个文件。

这些联系更像一张网，不是一棵只往下分叉的树。

![文件夹的层级，与需求、代码、测试之间的联系不同](assets/file-vs-graph.svg)

不是说文件不能存这种网。用链接、编号或一份表格就能先表达。难的是：**联系是否准确，修改以后有没有一起更新。**

例如可以先给需求编号：

```text
REQ-01：用户能纠正一项偏好
实现：update_preference()
检查：纠正后，下次任务使用新偏好
```

`REQ-01` 只是一个方便引用的名字，不是某种神秘格式。

## 3. repo.db 是一种设想，不是必须先建的东西

**数据库**可以先理解成“方便程序保存、查找和更新资料的系统”。`repo.db` 是把项目内容与联系一起保存的设想。

每次修改时，先拿出相关需求、实现和测试，而不是把整个项目都塞给 AI。这个局部展示叫**视图（view）**，就是同一份资料的一种看法。

像选课时只看自己的课表，而不是学校全部课程记录。

你现在的项目不需要立刻改成数据库。先维护有用的编号、链接和测试对应关系，就已经在解决真实问题。

## 4. 一个准确版本，和“一直在做的那件事”不同

第三篇介绍了 merge 和 rebase：一边是整合两条路线，一边是在新起点重新应用改动。

![合并与变基留下不同的历史结构](assets/merge-vs-rebase.svg)

假设你正在“增加偏好过期功能”。今天写了一版，明天改了一版，后来又接上最新主线。

这些版本内容不同，但你仍认为自己在做同一件事。

因此可以给两个编号：

- **版本编号**：准确标识这一版内容；
- **工作编号**：跟踪持续修改的同一件事。

**jj（Jujutsu）**是另一种版本管理工具。它用 `commit ID` 标识具体版本，用 `change ID` 跟踪这项持续变化的工作。ID 就是识别用的编号。

Git 也能保存变化历史，但 jj 把这种工作身份放到了更显眼的位置。

## 5. jj 的工作区为什么感觉不一样

Git 常用流程是：编辑 → add 选择内容 → commit 提交。

jj 把正在编辑的工作区也对应到一个可以继续修改的提交。多数命令运行时，会先保存文件变化的快照。

![Git 手动选入暂存区，jj 维护可继续修改的工作区提交](assets/jj-change.svg)

它不是每写一个字节都实时提交，也不是把过去全部删掉。

jj 还能先保存“这里有冲突”的状态，再安排解决。好处是操作不必总卡在一半；但有冲突的内容仍然要处理，不能直接当成可发布版本。

入门先理解：**工具可以把以前只是临时麻烦的东西，变成能保存和管理的对象。** 暂时不用背它的全部命令。

## 6. 两个 AI 助手，别一起编辑同一份目录

如果 A 刚读过文件，B 就把它改了，A 可能继续按旧内容写。两个窗口不等于两份独立工作。

**Git worktree，工作树**，可以让同一个仓库有多个工作目录，各自编辑、运行和测试，再把成果汇合。

像同一本作业的两份练习副本，共用历史，但桌面上的纸不是同一张。

```bash
git worktree add -b agent-ui ../project-ui
git worktree add -b agent-memory ../project-memory
```

这两条示例在已有仓库中建立新分支与目录。看不懂参数时，先让 AI 解释，再在练习仓库尝试。

终端窗口只隔离交互；**容器**可以隔离一部分运行环境，像给程序一个独立工作间。隔离程度取决于配置，大家共用的文件或服务仍可能相互影响。

## 7. 先各做各的，还是先排队

两种协作办法：

- **乐观协调**：先分开工作，最后检查能不能合起来。
- **悲观协调**：共享部分先排队，同一时刻只允许一个人改。

这里的“乐观、悲观”是技术名称，不是情绪评价。**锁**就是执行“先排队”的机制。

![先做后检查，与先拿锁再修改的取舍](assets/optimistic-vs-pessimistic.svg)

锁整个项目，容易安全但可能很慢；只锁一个文件，可能挡不住跨文件问题。还要考虑：助手中途退出，谁释放锁？拿到锁后，有没有重读新内容？

所以不是加一把锁就万事大吉。要看任务是否独立、哪里共享、怎样检查最终组合。

## 8. 文件没冲突，规则也可能冲突

例子：至少一人在宿舍等快递。

- 甲看到乙在宿舍，决定出门。
- 乙看到甲在宿舍，也决定出门。

两个人各自的判断都像是合理的，合起来却没人等快递。

代码也会这样：A 修改一个文件，B 修改另一个文件，Git 合并没冲突，整体却违反了“至少一人在”的规则。

**不仅检查每个人的成果，还要检查合起来的版本。** 历史、测试与授权记录仍然有用，不因为代码由 AI 生成就不必保存。

## 9. 第一版先帮上一件事，不用一口气做完整助手

**MVP，最小可行产品**，是一个够小、但能真正使用和验证想法的版本。

学习助手第一版可以只做：

```text
记录一项偏好 → 下次使用 → 用户纠正 → 检查是否改用新偏好
```

不必马上加邮件、日程、自动浏览器和复杂记忆系统。

也不必机械坚持“先用文件、永远不用数据库”。简单记录用文件方便；需要大量查询、多人并发和可靠更新时，数据库可能更合适。

关键是：**第一版要验证什么？什么结果说明我想错了？**

## 动手试一次

选择学习助手的一项功能：

1. 写一句能检查的需求，并给它编号。
2. 找出实现与测试，记录对应关系。
3. 修改需求，沿联系找出需要更新的地方。
4. 若并行开发，先写清双方的数据格式和整合检查。

## 本篇记住这四点

1. 可追踪性就是让需求、代码和证据之间有路可走。
2. jj 区分具体版本和持续修改的工作身份。
3. 独立目录减少覆盖，但最终组合仍然要验证。
4. MVP 先验证一件有价值的小事，不是先堆全部功能。
