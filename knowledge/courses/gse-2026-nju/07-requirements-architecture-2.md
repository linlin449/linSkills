# 生成式软件工程 07 · 需求和架构（2）

> 一句话：第六讲告诉我们“换一种表示，问题可能变简单”；第七讲继续回答“好在哪里”——**好的架构不是只做出一个能跑的解，而是为一类变化设计可继续生长的解空间；保存事实，让其他结果沿显式依赖计算出来，把到处同步状态的困难转成可以测试、重跑和审计的计算。**

本讲可以沿一条线理解：

```text
复杂性从哪里来
    → 用抽象减少必须同时理解的细节
    → 用共同规则允许未来组合
    → 把界面和业务结果写成状态的函数
    → 保存事实与规则，沿依赖计算结果
    → 让 AI 生成、检查这些计算，而不是猜测隐含同步要求
```

## 需求与架构分别在处理什么复杂性

“让学生方便选课”不是唯一规格，可能是先到先得、志愿排序或抽签；选定规格，也不意味着只有一种实现。**intent → spec → impl 的每一步都在作决定**，未经确认的决定越多，结果越容易偏离原意。

这里要区分两种复杂性：

| 类型 | 大白话 | 教务系统例子 | 能怎样处理 |
| --- | --- | --- | --- |
| **本质复杂性（essential complexity）** | 业务本来就难，不用计算机也绕不开 | 容量、先修、时间冲突、转专业课程认定 | 澄清规则、分解问题，不能靠换框架消除 |
| **附带复杂性（accidental complexity）** | 实现方式额外制造的麻烦 | 学生信息复制五份、日期格式不一致、规则散落多个页面 | 减少重复、统一接口、明确数据归属 |

需求工程要减少“到底要什么”的不确定性。说容量是 100 人还没说完：候补算不算？预留名额能否借用？特批能否突破上限？但需求也不是越长越好——**每多一条承诺，就多一条需要验证和维护的约束**。在 Agent 协作里，还会增加上下文长度、token 成本和遗漏约束的风险。

架构则分解本质复杂性、减少附带复杂性。把资格、容量、时间冲突分开建模，让学生选课、管理员补选和批量导入复用规则；不是把困难藏起来，而是给它们明确的归属。

判断架构是否有用，可以先问一句：**需求改一处，系统需要跟着改多少处？** 这不是唯一指标，但很能暴露不必要的耦合。

## 尊重“小脑袋”：抽象不是术语，而是减轻认知负担

Dijkstra 在《Notes on Structured Programming》中强调人的理解能力有限。能在脑中追踪十个状态，不代表能用同样的方法追踪一万个状态。解决办法不是假装自己能记住一切，而是借助：

- **枚举**：检查有限分支有没有漏；
- **归纳**：理解循环和递归如何从小问题推进到大问题；
- **抽象**：使用一个操作时依赖它承诺的效果，不必重新展开内部全部细节。

可以把分层想成一串“珍珠项链”：每层封装一项决定，上层使用下层提供的词汇。可替换并不只是“函数签名一样”——实现还必须维持调用者依赖的语义承诺，和第五讲的契约相接。

**决定的顺序同样重要。** 如果过早把“图像”规定成“逐行存储的图像”，中间各层都要理解“行”；推迟这个表示细节，上层就可以继续只谈图像。细节传播越远，替换它通常越贵。

### 对象与协程：分别组织数据和控制流

《Structured Programming》中的 SIMULA 例子展示两种分解：

- **对象**把相关状态与操作放在一个概念里；
- **协程**能暂停并保留局部状态与执行位置，之后恢复，让对等的程序片段不必硬塞进“谁调用谁、谁返回给谁”的关系。

两个游戏程序对弈时，双方都要计算、交出一步、等待回应再继续。协程让双方保留自己的流程；它并不自动意味着多核并行，解决的首先是控制流组织问题。

讲义还串起了三个抽象层：

```text
TWLIST：双向链表操作
    → MINISIM：模拟时间、等待、唤醒
    → 车间模型：请求机器、加工、释放机器
```

上层获得业务词汇，就不必在每次加工时重新处理链表连接。**抽象的价值，是让使用者可以暂时忘掉已经解决的细节。**

用 AI 读经典时，也应围绕具体证据提问：“这一层引入了什么概念？调用者因此不再关心什么？对应哪段代码？”而不是让它只写一段“这本书很经典”的空泛总结。代码位置和页码仍需回到原文核对。

## 好架构设计的是解空间，不只是一个解

一个好名字可以承载已经理解过的知识。说“队列”“事务”“选课资格”，就不必每次展开其全部实现；但名字必须对应稳定的含义，光把文件夹叫 `Model` 不会自动获得抽象。

Guy L. Steele Jr. 的《Growing a Language》提供了本讲的重要视角：**不仅设计今天可用的东西，也设计允许后来者继续创造的规则。** 规则固定各部分如何配合，同时保留以后可以填入的空位。

放回软件架构：

- 今天固定数据交换格式，未来允许新增处理步骤；
- 今天固定接口与契约，未来允许替换实现；
- 今天明确扩展点，未来增加能力时不必推翻全部已有代码。

![一个固定的解与可继续扩展的解空间](assets/solution-space.svg)

**开放不等于什么都不规定。** 没有接口和约束，新增组件也不知道怎样合作；把一切都固定，又不给未来留空间。架构要回答的是“什么现在固定、什么留给后来者”。

这也不是鼓励为所有想象中的需求提前造插件系统。更合理的做法是：根据已经看到的变化方向，保留有价值的替换与组合边界，并检查它是否真的减少修改成本。

## 三个经典系统：共同规则如何让应用继续生长

### UNIX：小工具能组合，靠的是共同接口

“每个程序做好一件事”还不够。互相不能连接的小工具，仍是一堆孤岛。UNIX 用文本流和通道约定，让输出可以给人看、存成文件或送给下一个程序。

示例组合（理解工具能力，不是本讲必须照抄的命令）：

```text
书目 JSON → jq 提取书名 → fzf 让人选一本 → 下游处理结果
```

人的判断也可以插入流水线。`xdotool` 则把部分 X11 窗口操作变成命令接口，使窗口选择与激活可以组合；不能据此假设它适用于所有桌面平台。

可靠组合还要约定这些细节：

- 标准输出放数据，标准错误放诊断信息；
- 退出状态报告执行结果；
- 给机器读的输出不要夹进进度条和颜色控制符；
- 格式、分隔符、选项与操作数的解析要明确；
- 文件名可能含换行，“一行一条”并不适用于所有数据。

**工具作者没写好所有未来用途，但提供了创造用途的规则。**

### 关系数据库：逻辑关系与物理存储分开

Codd 的关系模型让用户描述“数据意味着什么”，不必亲自决定每条记录放在哪个磁盘页、每次查询怎样扫描。

图书馆里“读者借走馆藏”是一组逻辑关系，可以据此查读者借了哪些书，也可以反查某册书被谁借走。SQL 描述想得到什么结果，优化器选择执行计划，事务组织需要整体处理的读写。

数据库设计者没有预先列出全世界的报表，却提供了关系、约束和查询的表达能力。**用户能提新问题，底层也能改存储方式，双方获得一定的独立演化空间。**

### Internet：局部替换时，整体仍能协作

应用、安全与传输、IP、链路各层负责不同问题，应用不必为每段物理链路的变化重写业务逻辑。

RFC 1958 把架构放在持续变化中理解，像城市不断改造街道和建筑，却仍继续运转。Telnet、SSH、HTTPS 等上层用途会演化，通用通信能力仍然服务它们。

三者的共同价值不是“功能很多”，而是**通过稳定的协作边界，让设计者没有预料到的应用也能长出来**。

## MVC：让变化有归属，而不是每个页面各写一遍规则

朴素 Web 应用可以是“一个页面、一段请求处理、一组 SQL”。Java Web 和 JSP 让页面生成更容易，但在模板中嵌入代码，也很容易把业务规则塞进页面：学生选课页检查容量，管理员补选页再检查一次，批量导入又写一份。规则一变，就要找所有入口。

MVC 用三个职责分开这个问题：

| 组成 | 负责什么 | 不应被误解为什么 |
| --- | --- | --- |
| **Model** | 数据、状态、业务规则 | 不只是数据库表或 ORM 对象 |
| **View** | 展示数据与结果 | 不该拥有另一份独立业务规则 |
| **Controller** | 接收输入，协调业务处理 | 不该堆进全部业务逻辑 |

课表从列表改成周历，主要是展示变化；选课限制修改，主要是规则变化；新增管理员入口，应复用业务能力，并明确其授权差异。

这里的重点不是背三层名称，而是**同一项决定不再散落在每个页面里**。MVC 早期面向交互式界面，后来有不同 Web 实践，不能把所有实现硬当成同一种数据流。

## MVVM 与 React：界面状态也是需要建模的状态

同一份课程数据，搜索关键词、选中项、展开的菜单不同，界面就不同。这些信息通常不存进业务数据库，但仍然是状态：

```text
View = render(Model, ViewState)
```

**是否持久化，和是否值得建模，是两回事。** 如果界面状态藏在零散控件和回调里，人就得记住“点这里还要改那三处”。

### Vue / MVVM：把依赖表达出来

MVVM 的 ViewModel 组织面向展示的状态与行为。课程筛选里，课程数据和 `query` 是输入，`visibleCourses` 是它们的计算结果。

Vue 的 `computed` 可以表达这个依赖；`v-model` 把值传递和输入事件更新包装起来。双向绑定并不意味着业务数据可以在所有层之间任意改写。

### React：状态快照与派生结果

React 用属性与状态描述当前界面，事件通过更新函数请求下一次渲染。`setQuery` 不会立即改变当前渲染已经拿到的 `query`；下一次渲染使用新状态。

既然可见列表能从课程数据和筛选词算出来，**就不必再存一份独立的列表状态**。否则三者容易不同步。

下面是笔记整理的伪代码，不是课堂原始代码：

```text
输入事实：courses
界面状态：query
派生结果：visibleCourses = filter(courses, query)
界面输出：render(visibleCourses)
```

Vue 和 React 的具体机制不同，却都把“结果依赖什么”放在显眼位置。这条主线接下来会从界面延伸到业务系统。

## 把复杂性挪进 Model，还没有解决复杂性

CRUD 与 MVC 对许多局部信息管理很有效。但订单可能跨越下单、锁库存、支付、风控、发货、退款、售后、对账；毕业审核也不只是一个学分总数。

把所有代码搬到 `Model/` 目录，只是挪了位置，没有分解这些长流程里的责任、事实和依赖。

### 复式记账：有不变量，但平衡不等于业务正确

复式记账要求借方合计等于贷方合计，资产、负债和权益之间也有可检查关系。借入资金时，存款与债务同时增加；归还本金，两者同时减少。“借”“贷”是记账方向，不能按日常借入、借出理解。

这些约束很有用，但**账平了，不等于账记对了**：分类错误、重复记录一笔平衡分录，都可能照样通过算术检查。还要核对原始凭证、业务含义和记账动作的对应关系。

### LLM as a Compiler：AI 翻译动作，程序确定其含义

讲义的记账工具结合事件溯源与“LLM 作为编译器”：

```text
原始凭证与业务材料
    → LLM 提出结构化记账动作
    → 检查动作的类型、金额、前置约束和业务对应关系
    → 程序按确定规则执行
    → 计算资产负债表、利润表、现金流量表
```

案例里有财务费用 **75 元**、利息收益 **22.07 元**。按案例规则，货币资金净变化为：

```text
22.07 - 75 = -52.93 元
```

报表相关数字应由同一组动作与规则产生，不是让模型逐格猜测、填数。薪酬结算也要区分确认费用、形成应付和实际支付，避免付款时又记一次费用。

**模型负责材料到动作的翻译，程序负责动作的确定语义；动作是否符合真实材料，仍需要核验。** 这是“规约与实现之间的 gap”在真实业务中的落地，不是“换成 LLM 就不用审核”。

## 过去、现在、未来：事实、视图和预期分开

只存余额和一个状态字段，容易把不同历史挤成同一种表示，也容易把期待与已发生事实混起来。

- **过去：已经发生的事实**，例如支付已完成、费用已确认；
- **现在：事实经规则计算出的视图**，例如当前余额、待结算金额；
- **未来：尚未兑现的预期或待执行命令**，例如希望付款、预计收回应收款。

“要求付款”和“付款已完成”不能记成同一种事件。已支付又退款，与从未支付，可能净现金变化相同，却不是同一段历史。

事件溯源通过保存事实、追加更正或冲销来解释今天的状态。“过去不可更改”在这里是业务审计原则：**不要靠悄悄抹掉历史解释当前结果**，并不是免除隐私、保留期限等实际约束。

重算还有两个前提：

1. **要恢复当时结果，保留当时规则和外部输入**，不能用今天的汇率或培养方案冒充过去依据。
2. **重放内部计算，不重复执行外部动作**，不能因为重建余额而再次付款。

第六讲已经区分“恢复历史”和“按新规则重算”，这一讲进一步把它们放进事实与计算的模型里。

## 教务系统：让每个毕业结论都有计算路径

成绩、已通过课程、总学分、分类学分、“是否满足条件”若都被当成独立可编辑字段，改一门成绩就要记得更新全部副本，系统很容易出现互相矛盾的多个“现在”。

更清楚的表示是：

```text
选课、成绩、更正、课程认定与审批记录
    + 适用规则及其版本
    → 已通过课程
    → 去重、替代、分类后的学分
    → 课程准出条件
```

![独立维护多份结果与事实驱动的派生计算](assets/facts-to-derived-state.svg)

课程准出条件还不是全部毕业条件：毕业设计、资产归还等要进入各自明确的判断。成绩从不通过改为通过，系统应记录更正，并重新计算受影响的结论；特批则保存批准对象、范围和依据，不能只把最后的“通过”布尔值改掉。

**数据依赖显式化，才知道结果来自哪里，哪些输入变化会影响它。** 但画出依赖图本身不会自动重算，还需要失效检测、计算顺序、更新机制和错误处理。正式发布的决定也不能因为新规则重算就被悄悄覆盖，要经过适用的复核流程。

## 从状态一致性，转向计算正确性

讲义对 SQL 有一个带挑衅性的批评：跨数据的任意计算关系没有被充分作为一等公民表达、维护，称之为一种“Billion Dollar Mistake”。

**这应理解为架构视角的批评，不是“SQL 不支持依赖计算”的技术结论。** SQL 有查询、视图、约束，数据库也有物化视图；真正困难的是跨数据库、应用逻辑、缓存和界面的整条链：基础数据变了，谁发现失效、谁刷新结果、谁记录其来源？

MVVM、React、Dataflow、Event Sourcing 在不同层次，把依赖放到显式表示里；不是同一种技术，也不应说它们全是为修复 SQL 而诞生。

本讲的设计原则可以压缩成一句话：

> **保存足以重建其他信息的事实依据（source of truth），其他状态尽可能作为计算结果；可以缓存，但必须知道来源、失效条件和重建方式。**

人工业务决定也属于需要保存的依据。能推导的结果则尽量别再安排一个独立编辑入口。这样，困难从“谁记得同步所有副本”，转成“这段计算是否正确”：

- 给定输入可以重跑；
- 可以写边界测试与性质测试；
- 可以检查每一步的来源和规则；
- 可以在明确范围内修正规则、重新计算。

复杂性没有消失，但变得更可定位、更容易验证。**这正是生成式软件工程需要的：让 AI 面对明确的事实、规则和依赖，而不是到处猜测哪些字段必须一起改。**

## 实践延伸：用自己的知识库检查这套原则

下面是将课程思想应用到当前知识库的整理建议，不是课堂原例。

| 环节 | 对应到知识库 | AI 可以帮助什么 | 要验证什么 |
| --- | --- | --- | --- |
| 事实依据 | Markdown 正文、frontmatter、真实目录 | 整理内容和直接关系 | 内容有来源，`related` ID 存在 |
| 派生结果 | catalog、graph、渲染页面、文章目录 | 编写构建和目录提取逻辑 | 重新构建能一致生成，不手改 `dist/` |
| 界面状态 | 搜索词、当前文章、图谱范围、缩放 | 实现交互，检查状态切换 | 当前关联只展示约定范围，切换后不残留旧状态 |
| 可扩展边界 | 内容不绑定某一种网页实现 | 对比接口和替换方案 | 换界面不需要重写全部笔记 |

明天就可以做的四件事：

1. 找一个重复存储的结果，写清它的事实输入与规则，决定它究竟是权威数据还是缓存。
2. 让 AI 画出依赖链，再用代码和数据核对；遗漏的审批或外部输入不能靠猜。
3. 选一种真实需求变化，检查它牵动几个模块，是否可以沿已有接口落地。
4. 为派生计算补一个可重跑测试，再补一个独立核验——模型生成计算和测试时，可能共享同一个误解。

## 总结：本讲真正要记住的

1. **业务自带的是本质复杂性，实现制造的是附带复杂性**；架构分解前者、减少后者。
2. **抽象让有限头脑暂时忘掉细节**，要检查每层承诺，而不是只学名字。
3. **好架构设计可继续生长的解空间**：共同规则要稳定，有价值的变化要有落脚点。
4. **UNIX、关系数据库、Internet 都把合作规则做成了基础能力**，支撑后来者创造新应用。
5. **MVC 给变化分配职责，MVVM/React 把界面依赖显式化**；派生结果不应随意再存成独立状态。
6. **LLM 可以把材料编译成受约束动作**，但算术正确不等于业务翻译正确。
7. **过去是事实，现在是计算视图，未来是预期**；重建状态不能重复外部副作用。
8. **事实、规则和依赖越清楚，AI 越能生成和检查可重跑的计算**；我们要让每个重要结果回答“我是怎样算出来的”。
